3. Module Requirements
3.1 Module 1 â€” Inventory Management
Manages the complete lifecycle of clinic inventory including procurement, stock tracking, adjustments, inter-branch transfers, low-stock alerting, expiry control and supplier relationships.

3.1.1 Functional Requirements
Inventory Master: Maintain a master catalogue of all inventory items (medicines, consumables, grooming supplies, pet food). Each item tracks SKU, category, unit of measure, HSN code, tax rate and reorder level.
Stock Entry: Record goods received from suppliers with batch numbers, MRP, purchase price, expiry date and quantity. Automatically update stock ledger on confirmation.
Stock Adjustment: Allow authorised users to increase or decrease stock counts with a mandatory reason (damage, theft, audit correction). All adjustments logged with user and timestamp.
Stock Transfer: Initiate and approve transfers between branches/locations. Transfer requests move through Pending â†’ Approved â†’ Dispatched â†’ Received states.
Low Stock Alert: System automatically triggers alerts (in-app notification + email) when item quantity falls below the configured reorder level. Dashboard widget highlights critical items.
Expiry Management: Daily batch job scans for items expiring within 30/60/90 days. Expired items are quarantined automatically and flagged for disposal or return to supplier.
Supplier Management: Maintain supplier profiles with contact info, payment terms, lead time, GST number and product catalogue. Track purchase history per supplier.

3.1.2 Non-Functional Requirements
Stock updates must reflect within 2 seconds of entry confirmation.
Audit log retained for minimum 7 years (compliance).
Barcode / QR scanning support for stock entry and adjustment.

3.2 Module 2 â€” Billing Management
Provides a unified billing engine covering all revenue streams of the clinic. Generates GST-compliant invoices that can be printed, emailed or downloaded as PDF.

3.2.1 Functional Requirements
Consultation Billing: Auto-populate consultation fees from doctor tariff master. Support multi-visit billing within one encounter and package/bundle pricing.
Lab Billing: Line-item billing for each diagnostic test ordered. Integration with Lab module to trigger test only after billing confirmation.
Pharmacy Billing: Fetch dispensed items from prescriptions, apply pharmacy margin, compute GST (IGST/CGST/SGST based on supply state). Reduce inventory automatically.
Grooming Billing: Itemise grooming services from the grooming module. Support add-on services and tip collection.
Miscellaneous Charges: Handle OT charges, procedure fees, accommodation, oxygen charges etc. with configurable charge codes.
GST Calculation: Auto-derive CGST+SGST or IGST based on customer GSTIN and clinic state. Apply correct tax slabs per HSN/SAC code. Generate GSTR-1 compatible data.
Invoice Generation: Produce sequentially numbered invoices with clinic letterhead, QR code, payment summary, itemised breakdown and digital signature. PDF rendered server-side.

3.3 Module 3 â€” Payment Management
Handles all modes of payment collection, reconciliation and refunds. Integrates with payment gateways for digital transactions.

3.3.1 Functional Requirements
Cash Payment: Record cash collected, print receipt. Cashier reconciliation report at day-end.
Card Payment: POS terminal integration via payment gateway SDK. Capture terminal reference for audit.
UPI Payment: QR code generated per invoice. UPI gateway callback confirms payment and auto-updates invoice status.
Online Payment: Payment link sent via SMS/email. Supports Razorpay/PayU/Stripe. Webhook-based status updates.
Refund Management: Initiate full or partial refunds. Refund to original payment mode. Refund requires dual authorisation (billing staff + admin). Webhook confirms gateway refund.
Transaction History: Immutable ledger of all transactions per patient, per day, per doctor and clinic-wide. Exportable to CSV/PDF.

14. Architectural &amp; Compliance Addendum â€” v1.1
This section addresses six critical architectural and compliance gaps identified during technical architecture review. These requirements are mandatory for all Phase 1 implementation and must be treated as acceptance criteria, not suggestions.

14.1 Concurrency &amp; Idempotency (The Double-Click Problem)
Risk
Race conditions in financial and inventory operations can cause duplicate invoices, double-charges, and negative stock levels â€” all legally and operationally unacceptable.

14.1.2 Inventory Locking â€” Preventing Negative Stock
The current_stock column in inventory_items requires strict concurrency control:
Pessimistic Locking (Phase 1): Use SELECT ... FOR UPDATE NOWAIT when reading stock before dispensing. If lock cannot be acquired within 500ms, return HTTP 409 with ERR_STOCK_LOCK_TIMEOUT. Simple to implement in a monolithic deployment.
Optimistic Locking (Phase 2 â€” Microservices): Add a version INTEGER column to inventory_items. All update queries must include WHERE version = :expected_version. If 0 rows updated, retry up to 3 times then return HTTP 409 with ERR_CONCURRENT_MODIFICATION.
Hard Constraint: A CHECK constraint at the database level enforces current_stock &gt;= 0 as a last line of defence, regardless of application logic.

14.4 Financial Edge Cases â€” GST Credit Notes
14.4.1 Legal Requirement
Under the Indian GST Act (Section 34), a registered supplier must issue a Credit Note when: (a) the taxable value or tax on a supply is found to exceed the actual amount, or (b) goods are returned by the recipient. A Credit Note is a legally required document â€” a simple refund record is not sufficient for GST compliance.

14.4.2 Credit Note Workflow
Refund initiated by billing staff and approved by admin (existing dual-auth flow).
System validates: is the original invoice finalised and GST-submitted? If yes, Credit Note is mandatory.
System generates Credit Note with: unique sequential credit_note_number (CN-YYYY-NNNN), reference to original invoice_number, line-item-wise reversal of GST (CGST/SGST/IGST), reason code, and authorised signatory.
Credit Note is linked to the original invoice in the database.
Credit Note is included in GSTR-1 return for the relevant tax period.
Payment refund is processed only after Credit Note is generated.

14.6.3 ERR_GATEWAY_TIMEOUT â€” Special Handling Required
Gateway timeout is the most operationally dangerous error in a payment system. The system MUST NOT treat it as a failed payment. The correct flow:
Payment request sent to gateway â€” no response within 10 seconds.
System sets payment status to UNKNOWN (new status in addition to PENDING/SUCCESS/FAILED).
System returns ERR_GATEWAY_TIMEOUT to client with the internal payment_id.
Client UI displays &apos;Payment status unknown â€” do not retry. Please check payment status.&apos; with a Check Status button.
Background job polls gateway for payment_id status every 30 seconds for up to 10 minutes.
On confirmed SUCCESS or FAILED, system updates payment record and pushes notification to billing staff.
Under no circumstances should the client UI allow a re-submission of the same payment without first confirming UNKNOWN status is resolved.
